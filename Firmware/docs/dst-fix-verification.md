# Pacific daylight saving fix

Date: 2026-11-05

The English timezone path previously passed an API offset snapshot to
`configTime`. That cannot describe seasonal transitions. The current fix maps
`America/Los_Angeles` to `PST8PDT,M3.2.0,M11.1.0` and uses `configTzTime` at
boot, hourly resync, and daily location refresh. Clock rendering and the
07:00–20:00 day-boost schedule continue to use `localtime_r`.

This supersedes the numeric-offset mechanism described in the July time-sync
design, not its hourly resync, daily location refresh, or day-boost decisions.
SNTP restart requests synchronization; it does not guarantee a successful reply.

The rule matches the upstream ESP8266 timezone table:
https://github.com/esp8266/Arduino/blob/master/cores/esp8266/TZ.h

Unknown zones retain the existing fixed-offset behavior. Invalid API replies
retain the last valid in-memory timezone. On a fresh boot before successful
discovery, the timezone remains UTC; no new persistent timezone setting is added.
Offline seasonal transitions work after discovery while system time remains valid.

`/time-debug` now exposes `timezone`, `tz_rule`, `local_time`, `is_dst`, and the
effective `tz_offset_sec`, rather than a stale API offset snapshot.

## Checks

Run from Firmware in a POSIX host environment (WSL Ubuntu was used):

```sh
g++ -std=c++11 -Wall -Wextra -I Holo-fw/lib/ArduinoJson-6.x/src tests/timezone_test.cpp -o /tmp/holoclock-timezone-test
/tmp/holoclock-timezone-test
```

Observed exit 0, zero failures: eight local-time cases (four transition-boundary
cases and four fallback/year-boundary cases), seven malformed/unsuccessful API
responses, valid JSON discovery, winter snapshot rule selection, and invalid
direct inputs. The test executes the same helper and vendored ArduinoJson used
by firmware. It uses host libc, not ESP32 libc.

The negative control compiles with `-DHOLO_DST_BASELINE`, using the old fixed
summer offset string generated by Arduino ESP32 `configTime`. Observed exit 1
with three mismatches, including fall 02:00 instead of 01:00. Assertions were
not weakened between the negative control and passing run.

Independent read-only review found no substantive defect in the task delta.
Existing firmware changes predate this task and are outside that review.

Both `Holo_Releases` and `Holo_Debug` passed with PlatformIO (exit 0).
Release usage: 82,564 bytes RAM and 1,667,678 bytes application flash.
Existing vendored-library/framework warnings remain; see `dst-review.md`.

## Hardware boundary

COM9 was enumerated as USB-SERIAL CH340 and its running serial output contained
clock IMU/now-playing messages. Before flashing it reported no WiFi, and the
configured address 192.168.1.225 did not answer `/time-debug`. No physical
display or actual seasonal transition has been observed in these host checks.

## Deployment

`pio run --project-dir Holo-fw -e Holo_Releases --target upload --upload-port COM9`
completed with exit 0, flash hashes verified, and the normal post-upload reset.
The chip identified as ESP32-PICO-D4 revision 1.

Uploaded release binary SHA-256:
`82e7b09f53b9a3d11e7629ef647787e1478ab3a2327c39c32665ea876590c74b`.
The 2,669-entry source manifest captured before upload had zero changes afterward.
The pre-task release binary and watcher source are saved under the local temporary
directory `holoclock-dst-before` for rollback/comparison.

After upload, read-only `/time-debug` checks showed connected WiFi, valid time,
`America/Los_Angeles`, `PST8PDT,M3.2.0,M11.1.0`, offset -28800 and `is_dst=false`.
The reported local clock advanced from 2026-11-05 18:45:11 to 18:45:58.
The day-boost mode remained auto.

A less-than-five-second comparison against the Windows host failed: the device
was about 14 seconds ahead. Independent UDP NTP queries to time.google.com and
time.cloudflare.com also measured about +14.18 seconds against the host, so
the Windows host was not a valid close-accuracy reference. This is separate
from the passing timezone checks. No physical display or simulated on-device
seasonal transition was exercised.
